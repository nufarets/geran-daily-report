# Ежедневная архивная сводка

Проект собирает уже опубликованные сообщения из открытых Telegram-каналов, формирует ежедневный отчёт и сохраняет его в GitHub. Это архивная обработка открытых публикаций, а не система оперативного оповещения.

## Результат

Для периода «предыдущий день — текущий день» генератор создаёт:

- `reports/YYYY-MM-DD.md` — датированный отчёт, где дата соответствует дню окончания периода и публикации;
- `reports/latest.md` — последний доступный отчёт по постоянному пути.

Повторный запуск идемпотентен: если отчёт уже опубликован и его содержимое не изменилось, новый коммит не создаётся. Workflow добавляет в коммит только изменения внутри `reports/`.

## Источники

Основные каналы:

- [`geranium_chronicles`](https://t.me/geranium_chronicles) — ежедневная хроника; если публикация разбита на две части, части рассматриваются как одна сводка; свежая одиночная часть получает пять минут на возможное продолжение;
- [`kpszsu`](https://t.me/kpszsu) — первое сообщение об ударных БПЛА и, при наличии, итоговая сводка ППО.

Дополнительные источники для установления опубликованных точек пуска:

- [`ua_ppo_monitor`](https://t.me/ua_ppo_monitor);
- [`Ukrainian_Intelligence`](https://t.me/Ukrainian_Intelligence);
- [`StrategicaviationT`](https://t.me/StrategicaviationT).

Сбор выполняется через публичные веб-превью каналов вида `https://t.me/s/<channel>` и отдельных сообщений. Telegram Bot API, пользовательская сессия и закрытые данные не используются.

## Правила формирования

### Период и начало хронологии

Для отчёта, например, за `17.08.2026–18.08.2026` первое упоминание ударных БПЛА ищется в `kpszsu` после `12:20` **17 августа**, то есть в предыдущий день периода.

Распознаются сообщения с обозначениями 🛵 и 🏍, а также текстовые упоминания ударных и групп реактивных БПЛА без значка. Смена значка источником не должна сдвигать начало хронологии. Если опубликованный интервал события пересекает отсечку начала, интервал сохраняется целиком в формулировке источника.

### Хронология

- Учитываются только сообщения, относящиеся к БПЛА типа «Герань».
- События группируются по областям: сначала заголовок области, затем время и населённый пункт.
- Каждая область выводится отдельной строкой, а каждое событие под ней — в формате `HH:MM - населённый пункт`.
- Если в источнике указана область, но не указан населённый пункт, строка оформляется как `HH:MM - взрыв в области`.
- Несколько времён одного события или населённого пункта могут быть объединены в одну строку.
- Названия известных населённых пунктов приводятся к именительному падежу: например, «Черновцов» → «Черновцы», «Бучи» → «Буча», «Шепетовки» → «Шепетовка», «Вознесенска» → «Вознесенск». Для них область определяется и без прямого указания в строке источника.
- Соседние текстовые части хроники объединяются по содержанию и времени публикации. Разрывы в номерах сообщений из-за фото и видео не мешают объединению частей, опубликованных с интервалом до 30 минут. Дополнения с соседними номерами допускаются в течение часа; посторонние сообщения и новая ежедневная хроника прекращают объединение.
- Граница суток определяется по явному переходу от дневных/вечерних часов к утренним во всей последовательности событий. Повторные ошибочные заголовки даты и разбиение на несколько частей не сбрасывают эту границу. После определения дней применяется обычная отсечка по первому сообщению об ударных БПЛА. Также распознаются опечатки вида `18:33.Город` и `20:50-20-55`.
- Если даты остаются противоречивыми (несколько переходов через полночь либо события позднее текущего окна сбора), отчёт не публикуется: следующая попытка повторяет сбор. Это защищает от публикации одной дневной части с ошибочной датой при отсутствии продолжения. При пересборке старого отчёта конец окна ограничен `12:20` дня окончания периода.

### Сводка ППО

Если итоговая сводка ППО в `kpszsu` уже опубликована, отчёт включает количество запущенных и количество сбитых/локационно потерянных БПЛА. Если к моменту формирования такой публикации нет, обе числовые строки пропускаются — значения не рассчитываются и не додумываются.

Для числа сбитых используются только БПЛА типа Shahed, Гербера и других типов из соответствующей строки сводки. Общий итог «збито/подавлено … цілей», включающий ракеты и «Бандероль»/«Дань-Т», не подставляется вместо количества БПЛА. Если отдельное количество БПЛА не указано однозначно, строка о сбитых пропускается.

Точки пуска берутся только из уже опубликованных сообщений перечисленных источников. Для резервного сбора учитываются подтверждённые пуски с `12:20` предыдущего дня до момента успешного формирования отчёта, но не позднее границы нового цикла в `12:20` дня окончания периода. Если хотя бы один резервный канал временно недоступен, публикация откладывается до следующей попытки, чтобы не зафиксировать заведомо неполный список. Для унификации применяются следующие замены:

| Публикация источника | В отчёте |
|---|---|
| Халино | Курск |
| Миллерово | Ростов |
| Навля | Брянск |
| Шаталово | Смоленск |
| Кача | Крым |
| Цимбулово | Орел |

Названия `Чауда`, `Гвардейское` и `Приморско-Ахтарск` сохраняются без замены.

## Расписание

GitHub Actions делает первую попытку ежедневно в `08:10`, затем повторяет попытки каждые 10 минут до `09:50`, каждые 30 минут до `11:40` и последнюю попытку в `12:10`. Часовой пояс задаётся явно как `Europe/Moscow`.

Основным планировщиком служит Cloudflare Worker `geran-daily-report-scheduler`. С `08:10` до `12:10` МСК он каждые пять минут проверяет наличие `reports/YYYY-MM-DD.md` и, если файла нет, запускает этот же workflow через GitHub API. Встроенное расписание GitHub сохранено как независимый резерв. Повторные внешние вызовы безопасны: генератор идемпотентен, а workflow использует единую очередь.

Повторные попытки нужны потому, что ежедневная исходная сводка может появиться позже обычного времени. Как только генератор создаёт новый отчёт, workflow коммитит его от имени `github-actions[bot]`. Если данных ещё недостаточно или отчёт уже существует без изменений, запуск завершается без коммита. При необходимости workflow можно запустить вручную через **Actions → Publish daily report → Run workflow**. В ручном запуске можно указать дату окончания периода в формате `YYYY-MM-DD` и при необходимости разрешить пересборку существующего отчёта.

GitHub запускает задания `schedule` приблизительно в указанное время и может задержать, а при особенно высокой нагрузке — пропустить отдельный запуск. Поэтому `08:10` — время постановки первой попытки в очередь, а не гарантия публикации минута в минуту; последующие попытки одновременно служат страховкой. Если к последней попытке в `12:10` отчёт всё ещё не сформирован, workflow завершается с явной ошибкой вместо скрытого успешного статуса; то же правило действует для ручного запуска. Запланированные workflow выполняются только из основной ветки репозитория; в публичном неактивном репозитории GitHub может отключить расписание после 60 дней без активности.

## Локальный запуск

Требуется Node.js 24 или новее. Внешних npm-зависимостей у проекта нет.

```bash
npm test
npm run generate
```

## Настройка нового репозитория

1. Создайте репозиторий в нужном GitHub-аккаунте и отправьте этот проект в его основную ветку.
2. В настройках репозитория разрешите GitHub Actions выполнять workflow и выдавать `GITHUB_TOKEN` право записи содержимого. В самом workflow запрошено минимальное разрешение `contents: write`.
3. Откройте вкладку **Actions** и выполните один ручной запуск для проверки.
4. Убедитесь, что после успешного запуска появился датированный файл в `reports/`.

Секреты для чтения публичных страниц не нужны. Если позже появятся закрытые источники или внешние API, их ключи следует хранить только в GitHub Actions Secrets, а не в репозитории.

## Внешний планировщик Cloudflare

Worker использует fine-grained GitHub token, ограниченный репозиторием `nufarets/geran-daily-report` и разрешением **Actions: Read and write**. Токен хранится только как зашифрованный секрет Cloudflare `GITHUB_ACTIONS_TOKEN`.

Первичная настройка:

```bash
npm install
npx wrangler login
npx wrangler secret put GITHUB_ACTIONS_TOKEN
npm run scheduler:deploy
```

Cron Cloudflare работает в UTC. Конфигурация запускает Worker каждые пять минут с `05:00` до `09:59` UTC; сам Worker разрешает dispatch только в окне `08:10–12:10 Europe/Moscow`. Перед каждым вызовом он проверяет наличие датированного отчёта, поэтому после успешной публикации дальнейшие попытки прекращаются автоматически.

## Ограничения публичного Telegram-превью

- Каждый ответ публичной веб-страницы показывает ограниченное окно сообщений; переход к более старым публикациям зависит от доступности пагинации Telegram.
- Telegram может временно ограничить запросы, вернуть неполную страницу или изменить HTML-разметку без предупреждения.
- Удалённые, отредактированные, закрытые и недоступные без авторизации сообщения невозможно гарантированно восстановить.
- Поздняя публикация, необычное оформление или нетипичное разбиение сводки на части могут потребовать ручной проверки.
- Автоматический отчёт отражает только данные, которые были доступны в источниках на момент успешного запуска; он не является первичным источником и не заменяет проверку оригинальных сообщений.

При временном сбое следующий запуск по расписанию повторит сбор. Если исходная сводка появилась после последней попытки в `12:10`, workflow нужно запустить вручную.
